# Hosted Docs Site (Phase 2b) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `apps/docs` — a hosted Starlight site documenting how to *use* the template, built with the template itself, with `packages/template/wiki/` rendered in place as its Internals section.

**Architecture:** A trimmed copy of the template — public docs only, no adapter, no auth, no Scalar — plus ~18 authored pages and a content collection that globs the wiki from outside the app root (verified possible). Static output; its own `package.json` and lockfile, like every project here.

**Tech Stack:** Astro 6 + Starlight, `@astrojs/sitemap`, `starlight-llms-txt`, `@ekline/starlight-contextual-menu`, Tailwind v4, `node --test`.

**Spec:** [`docs/superpowers/specs/2026-08-21-phase-2-monorepo-hosted-docs.md`](../specs/2026-08-21-phase-2-monorepo-hosted-docs.md), including its agreed information architecture. Read it first.

**Branch:** `pa-claude/docs-site`, worktree `.claude/worktrees/docs-site`. **Third in a stack:** its base is `pa-claude/monorepo-hosted-docs` (PR #10), which is based on `pa-claude/demo-login-private-docs-e4f30b` (PR #9), which is based on `main`. Never rebase onto `main`.

---

## The rule that governs every content task

**Every factual claim must be checked against the code as it actually is.** This documentation is the product for customers who will never read the source. A wrong file path, a stale option name, or a config example that does not work is a defect, not a typo — and this project has already shipped three of them (a comment that leaked into a rendered page, a `.env.example` claim that was conditionally false, a README quick-start that failed at step 3).

Concretely, for every page: open the file you are describing, run the command you are documenting, and verify the option exists. If the template's behaviour differs from what the source material says, **the template is right and the source material is stale** — fix the docs and report it.

Do not document behaviour you have not observed.

The site is the template minus the logged-in experience and the API reference. `packages/template/README.md` § *Don't need private docs?* already documents exactly that removal — so follow it literally. That builds the site **and** tests those instructions on a real run, which nothing has done before.

Read it in `packages/template/README.md` and do what it says — both paragraphs, including the second one about getting the plain static build back. **Follow it literally, and keep a note of every place the instructions are wrong, incomplete, or ambiguous.** That list is a deliverable of this task: those instructions ship to customers, and this is the first time anyone has run them.

### Task 2: Render the wiki in place

`packages/template/wiki/*.md` becomes the site's **Internals** section, read from outside the app root — verified possible: a `glob` loader with a `base` outside the project loaded files from an entirely different worktree.

The wiki files have no frontmatter (they open with an H1) and `docsSchema()` requires a `title`. Derive it from the H1 rather than editing the files: their in-repo readability is for the same person the file is written for.

**Files:**
- Create: `apps/docs/src/loaders/wiki.mjs`, `apps/docs/tests/wiki-collection.test.mjs`
- Modify: `apps/docs/src/content.config.ts`, `apps/docs/astro.config.mjs`
- Create: `apps/docs/src/pages/internals/[...slug].astro`

- [ ] **Step 1: Write the failing test first**

`apps/docs/tests/wiki-collection.test.mjs` asserts against the built output: every file in `packages/template/wiki/` produces a page under `/internals/`, each page's `<title>` matches that file's H1, and the body contains prose from the source file. Read the wiki filenames from disk rather than hardcoding them, so a new wiki file is covered automatically.

- [ ] **Step 2: Run it, confirm it fails** for the right reason (no such pages).

- [ ] **Step 3: Write the loader**

Wrap Astro's `glob` loader. For each entry, if frontmatter has no `title`, take the first `# ` heading as the title and strip that line from the body so it is not rendered twice (Starlight renders the title as the page's `<h1>`). Document *why* this exists — the alternative was prepending YAML to files whose in-repo readability is the point.

Point it at `../../packages/template/wiki` relative to the app root. Add a comment that this reads outside the project deliberately, so nobody "fixes" it into a copy step, which would reintroduce the drift the whole design avoids.

- [ ] **Step 4: Wire the collection, the route and the sidebar group**, then run the test until it passes. Paste real output.

- [ ] **Step 5: Confirm single-sourcing is real, not theatre**

Append a line to `packages/template/wiki/theming.md`, rebuild `apps/docs`, confirm the line appears in the built page, then revert. A copy step would pass every other check in this task and fail this one.

- [ ] **Step 6: Commit.**

### Tasks 3–7: The content

One task per IA section. **Before starting any of them, read
`apps/docs/CLAUDE.md` § "Who these docs are for" and § "Voice and structure".**
Those are the brief: five named personas, one job per page, one Diátaxis mode
per section, and cut ruthlessly. They are not decoration — the reviewer checks
against them.

The accuracy rule at the top of this plan applies to every page.

Source material to draw on — but verify, never transcribe:
- `packages/template/README.md`, `CHANGELOG.md`, `CLAUDE.md`
- `packages/template/wiki/{private-docs,api-reference,theming}.md`
- `packages/template/src/config/*.mjs`, `astro.config.mjs`, `.env.example`
- The root `README.md` for the adoption command

Each task: write the pages, wire the sidebar in `apps/docs/src/config/sidebar.mjs`,
run `npm run check` and `npm run build`, confirm every internal link resolves,
commit. Then a separate reviewer subagent audits it before the next task starts.

**Page counts below are ceilings, not targets.** If a section is honestly
shorter, make it shorter and say why. Length is not thoroughness.

### Task 3: Get started — *tutorial mode*

For the **Evaluator** (landing) and the **Adopter** (the rest). Up to three pages:

- **index** — what the template gives you, what it does not, who it suits. The
  Evaluator's whole visit. Answer fast; no feature tour.
- **quickstart** — create, install, run, make a first edit. One guaranteed path.
  No options, no alternatives. The create command is
  `npm create astro@latest -- --template ekline-io/ekline-docs-template-astro/packages/template`
  — **run it once and confirm before documenting it.**
- **deploy** — Vercel, Node, static: which features each supports, and the one
  setting that matters per target.

### Task 4: Configure — *how-to mode*

For the **Adopter**, and *writing content* for the **Author** — who is often not
a developer. Up to five pages: site basics; branding and theming; navigation and
the sidebar; writing content; search and AI (`llms.txt`, the contextual menu).

`wiki/theming.md` is maintainer-facing — rewrite for a customer, do not copy.
The writing-content page must stand alone for someone who never opens
`astro.config.mjs`.

---

### Task 5: API reference — *how-to mode*

For the **Adopter** who has an OpenAPI document. Up to two pages: adding your
document (`src/config/api-reference.mjs`), including **the two layout modes** —
`docs` (embedded, keeps the Starlight sidebar and lists operations in it) versus
`full` (Scalar's own shell) — what each suits and how to switch; and customizing
(what the template deliberately switches off, with the one-line restore for each,
plus `--scalar-*` theming).

`apps/docs` has no API reference of its own, so verify every claim against
`packages/template`, not against this site.

---

### Task 6: The logged-in experience — *how-to mode*

Mostly for the **Integrator**, who wants a contract and a sample and will read
nothing else. Up to four pages: how it works (three access levels; readers sign
in through *your* product; no user database here); setting it up (the env vars,
and the one endpoint your product implements, with the working sample); trying
it without SSO (the demo login — state the danger as plainly as `.env.example`
does); writing private and per-org content (the two collections, org folder
naming, and that `sidebar.hidden` is not access control).

Link to Internals for the constraints rather than restating them.

### Task 7: Reference — *reference mode*

Lookup for everyone. Dry, complete, scannable, tables over prose. Up to three
